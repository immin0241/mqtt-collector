- 코드: 브랜치 `phase-1-ingest-integrity` (수동 ack, 지속 세션, 무한 재시도, 이분법 격리 적용)
- 환경: WSL2 (Linux 6.6.87.2), Docker 29.8.0, `docker compose` 단일 호스트. 호스트 메모리 15.42GiB. CPU 사양은 기록하지 않았다.

- 판정 방법: 센서별 `max(seq) - min(seq) + 1 - count(*)`로 누락을 계산하고, `GROUP BY sensor_id, seq HAVING count(*) > 1`로 중복을 센다. 에뮬레이터의 `/stats`(`publish_errors`)로 발행 측 유실을 분리했다. `tools/reconcile`은 Phase 2 예정이라 아직 쓰지 못했다.
- 이 DB에는 이전 개발 데이터가 있어 `received_at > 16:50:57 UTC`로 이번 실행분만 집계했다.

## TC-02: DB 10초 중단

절차: `docker compose stop postgres` → 10초 대기 → `docker compose start postgres` → 30초 관찰.

| 판정 항목 | 목표 | 실측 |
| --- | --- | --- |
| panic | 0 | 0 |
| 앱 재시작 | 0 | 0 (`RestartCount=0`) |
| 일시적 오류 재시도 | 복구까지 반복 | 5회 (500ms, 1s, 2s, 4s, 8s 백오프), 복구 후 적재 재개 |
| 누락 | 0 | 0 (센서 3개 모두) |
| 중복 | 0 | 0 |
| 격리 | 0 | 0 |
| 메모리 | 상한 내 | 앱 컨테이너 6.3MiB |

관찰:
- 백오프 간격이 길어져(마지막 8초) DB가 돌아온 뒤 적재 재개까지 최대 백오프만큼 지연될 수 있다. `RetryMax`(30초) 선택의 비용이다.
- 10초 × 3 msg/s는 채널(600)을 채우지 못한다. **백프레셔가 실제로 걸리는 구간은 이 실험에서 검증하지 못했다.** TC-06에서 확인한다.
- `HealthWorker`도 같은 DB를 쓰며 장애 중 `Failed to persist health state` 로그가 매초 쌓였다. 수집 경로에는 영향이 없었으나 로그 양은 Phase 2에서 다룬다.

## TC-03: 브로커 10초 중지

절차: `docker compose stop broker1` → 10초 → `docker compose start broker1` → 30초 관찰.

| 판정 항목 | 목표 | 실측 |
| --- | --- | --- |
| 재연결·재구독 | 자동 | `Connection lost: EOF` 후 재연결, 두 토픽 재구독 (중지 약 15초 뒤. paho 재연결 간격 영향) |
| DB 중복 | 0 | 0 |
| 누락 | 0 | **1건 (센서 102)** |

누락 1건은 수집 측 유실이 아니라 **발행 측 유실**로 판단한다. 근거: 에뮬레이터 `publish_errors`가 0에서 1로 증가했고, 누락도 정확히 1건이다. 다만 어느 seq가 실패했는지는 에뮬레이터가 발행 로그를 남기지 않아 직접 대조하지 못했다. Phase 4의 발행 로그와 발행 측 버퍼링이 필요하다. 이 항목은 **"누락 0" 기준을 완전히는 만족하지 못한 상태**이며, 발행 측 유실을 분리하는 것이 선행 조건이다.

## TC-04: SIGKILL 후 재시작

절차: `docker kill` (SIGKILL) → 약 40초 뒤 `docker compose start app` → 20초 관찰. 이 사이 에뮬레이터는 계속 발행했다.

| 판정 항목 | 목표 | 실측 |
| --- | --- | --- |
| 재시작 후 누락 | 0 | 센서 101, 103은 seq 연속(누락 0). 102의 1건은 TC-03 발행 측 유실 그대로이고 추가 누락은 없음 |
| 중복 | 0 | 0 |
| 격리 | 0 | 0 |
| 재구독 | 자동 | 완료, 쌓인 backlog 소화 |

한계:
- `docker kill`은 Docker가 수동 중지로 취급해 `restart: on-failure`가 동작하지 않아 앱을 직접 시작했다.
- 센서 3개가 약 0.33초 간격으로 보내고 flush 간격이 2초라 kill 시점에 미커밋 배치가 거의 항상 존재했을 것이나, **kill이 커밋과 ack 사이에 정확히 걸렸는지는 관측하지 못했다.** 브로커의 재전달과 `ON CONFLICT` 흡수 건수를 지표로 보려면 Phase 2의 `dedup_total`이 필요하다.

## 추가 확인: TC-07 (실제 DB 경로)

`mosquitto_pub`으로 3건을 거의 동시에 발행(한 배치에 묶임): 깨진 JSON, 존재하지 않는 센서(9999, FK 위반), 정상 행(센서 101, seq 900001).

| 항목 | 결과 |
| --- | --- |
| 깨진 JSON | `sensor_data_rejected`에 `PARSE_ERROR`, 원문 payload 보존 |
| FK 위반 행 | SQLSTATE `23503`으로 이분법 격리, sensor_id/seq/원문 보존 (gorm이 감싼 `PgError`도 `errors.As`로 분류됨을 확인) |
| 정상 행 | `sensor_data`에 저장 (같은 배치의 문제 행 때문에 버려지지 않음) |
| 무한 재시도 | 없음 (각 1회 격리) |

이 확인은 3건으로 한 번 수행했다. 범위 밖 값은 CHECK 제약이 없어 격리되지 않는다(ADR-0003 미결). 확인용 격리 행 2건과 센서 101의 seq 900001 행은 개발 DB에 남아 있다.

## 브로커 큐 기본값 실측 (ADR-0004 보강)

오프라인 지속 세션 구독자에게 QoS 1 메시지 1,500건을 발행한 뒤 재접속해 수신 건수를 센다.

| 브로커 설정 | 수신 건수 |
| --- | --- |
| 기본값 (`max_queued_messages` 미지정) | 1,000 |
| broker1 (`max_queued_messages 60000`) | 1,500 (발행분 전체) |

기본 큐 한도 1,000은 문서와 일치한다. `max_inflight_messages` 기본값(20)은 이 실험으로 확인하지 못했다.
