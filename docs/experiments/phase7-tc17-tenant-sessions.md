# TC-17 재시험 — 테넌트별 세션 분리(ADR-0011) 후

- 날짜: 2026-11-12
- 목적: 한 테넌트가 폭주해도 다른 테넌트의 데이터가 유실·중복 없이 저장되는지, 지연이 어떤지 확인한다. 이전 결과는 [phase6-tc17.md](phase6-tc17.md).
- 한계: 각 조건 1회 실행(A/B 비교 포함). 통계적 의미는 없고 현상 확인용이다.

## 조건

| 항목 | 값 |
| --- | --- |
| 장비 | AMD Ryzen 5 7500F (6코어 12스레드), RAM 15.8 GB, WSL2 위의 Docker. 테스트와 컨테이너가 같은 머신을 쓴다 |
| 구성 | testcontainers: TimescaleDB, Mosquitto. 앱은 같은 프로세스에서 `app.Run` |
| 브로커 | `max_inflight_messages 600`, `max_queued_messages 60000`, persistence on (운영과 같음) |
| 앱 | `BatchSize` 300, `FlushInterval` 200 ms, `ChannelSize` 600, `TenantChannelSize` 100 (기본값) |
| 스키마 | migration 000011 (세로 구조). 테스트 payload는 `tilt_x`, `tilt_y`만 있어 메시지당 2행 |
| 폭주 | 테넌트 A의 센서 5개가 PUBACK이 허용하는 최대 속도로 발행 |
| 평온한 테넌트 | 테넌트 B의 센서 1개가 폭주 중 100 ms마다 1건 발행하고, 그 행이 DB에 보이기까지의 시간을 잰다 |
| 판정 | 대조 도구(`reconcile`)로 누락·중복·예상 외. 폭주량을 키운 조건은 평온한 테넌트 유실·중복 0, 폭주 테넌트 중복·예상 외 0 |

## 결과

| 폭주량 (A 합계) | 발행 소요 | B 저장 지연 p50 / p95 / max | B 유실 | A 유실 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 20,000건 (센서당 4,000) | 1.7 s | 190 / 205 / 269 ms | 0 | 0 | 폭주 종료 4초 후 전부 저장. 이전(세션 1개): p95 0.46 s |
| 150,000건 (센서당 30,000) | 9.9 s | 118 / 147 / 159 ms (프로브 45건) | **0** | 49,200건 (32.8%) | 폭주 종료 44초 후 안정. 이전(세션 1개, 가로 구조): 평온한 테넌트도 유실이 관측됨 |

### 대조: 이전 커밋을 같은 머신·같은 조건으로 재실행

커밋 `938449e`(가로 구조, 세션 1개)에서 `TC17_FLOOD_PER_SENSOR=30000`을 같은 방법으로 실행했다.
센서 1은 30,000건 중 29,362건, 센서 2는 29,347건을 저장했다(유실 약 2.1~2.2%, 3분이 지나도 복구되지 않음). 이전 기록(2.6%)과 같은 수준이다.
즉 이번 폭주 테넌트의 유실 증가(2% → 33%)는 이 머신에서도 재현되는 **수집 처리량 저하**다.

### 원인 분리: `InsertRows` 단독 처리량

`test/experiments/store_throughput_test.go` (`go test -tags experiment -run StoreThroughput`). 배치 300건 × 200회, 수신 경로·브로커 제외, 위와 같은 머신.

| 메시지당 측정값 수 | msg/s | rows/s | 배치(300건) 커밋 p50 / p95 |
| --- | --- | --- | --- |
| 1 | 11,079 | 11,079 | 26.8 / 30.1 ms |
| 2 (현재 테스트 payload) | 5,651 | 11,302 | 52.5 / 59.5 ms |
| 4 | 2,862 | 11,447 | 104.2 / 114.6 ms |

행 처리량은 약 11,300 rows/s로 일정하다. 메시지당 행이 늘면 msg/s가 그만큼 줄어든다. 가로 구조는 메시지당 1행이라 약 11,000 msg/s였다.
150,000건이 10초에 들어오면(약 15,000 msg/s) 수집 용량(약 5,700 msg/s)을 넘고, 백로그가 브로커 큐 상한을 넘어 폭주 테넌트의 메시지가 사라진다. 계산상 유실은 약 3만 건이고 관측은 4.9만 건이다. 차이는 수신 경로(핸들러, 채널, ack)의 오버헤드로 추정하며 분리해서 측정하지 않았다.

## 해석

1. **격리는 작동한다.** 폭주 테넌트의 브로커 큐가 넘치는 동안에도 평온한 테넌트는 유실 0건, 지연 p95 150~205 ms였다. 이전에는 같은 조건에서 평온한 테넌트의 유실이 관측됐다(ADR-0011 선택지 B의 목표 달성).
2. **폭주 테넌트 자신의 유실은 남는다.** 그 테넌트의 세션 큐가 넘치면 PUBACK 한 메시지가 사라진다. 이 유실은 이전보다 커졌는데 원인은 격리가 아니라 ADR-0012의 쓰기 비용이다.
3. 세로 구조는 행 처리량이 같아도 메시지 처리량을 지표 수만큼 낮춘다. 개선 후보(COPY, 배치 크기, 인덱스·트리거 비용)는 Phase 7에서 측정한 뒤 선택지로 제시한다. 지금은 구현을 바꾸지 않았다.

```bash
TC17_FLOOD_PER_SENSOR=30000 go test ./test/integration/ -run TestTC17 -v -timeout 20m
# InsertRows 단독 처리량
go test -tags experiment -run StoreThroughput -v ./test/experiments
```
