# INSERT 방식 × 배치 크기 × DB 왕복 지연

- 날짜: 2026-11-13
- 목적: 쓰기 경로의 처리량을 좌우하는 요인을 가른다. TC-06 5분 조건 미달([phase7-tc06-5min.md](phase7-tc06-5min.md))과 세로 구조의 쓰기 비용(ADR-0012)에서 나온 질문이다. 결과는 구현을 바꾸는 근거이며, **이 실험에서는 구현을 바꾸지 않았다.**
- 한계: 각 조합 1회, 조합당 약 40,000행. 통계적 의미는 없고 경향을 보는 용도다.

## 조건

| 항목 | 값 |
| --- | --- |
| 장비 | AMD Ryzen 5 7500F (6코어 12스레드), RAM 15.8 GB, WSL2 위의 Docker. 클라이언트와 DB가 같은 머신 |
| DB | TimescaleDB 컨테이너, migration 000011~000012 (세로 구조, 인덱스·트리거·유니크 키 포함, 압축 정책 기본) |
| 클라이언트 | pgx 연결 1개 (저장 워커가 단일 고루틴인 것과 같은 조건) |
| 데이터 | 메시지당 측정 2행(tilt_x, tilt_y). 센서 5개, seq 단조 증가. 행 수 = 배치 × 2 |
| 지연 | DB 앞 FaultProxy로 방향당 0 ms / 20 ms (왕복 0 / 40 ms) |
| 코드 | `test/experiments/insert_strategies_test.go` |

방식:

| 이름 | 내용 | 왕복 |
| --- | --- | --- |
| multirow-tx | **현재 구현.** BEGIN + 다중 행 VALUES INSERT ... ON CONFLICT DO NOTHING RETURNING + COMMIT | 3 |
| multirow | 트랜잭션 없이 같은 문장 하나(문장 자체가 원자적) | 1 |
| unnest | 트랜잭션 없이 배열 파라미터 6개 + `unnest` INSERT ... ON CONFLICT DO NOTHING | 1 |
| copy | BEGIN + 임시 테이블 + COPY + INSERT ... SELECT ON CONFLICT DO NOTHING + COMMIT | 4 이상 |

## 결과 (rows/s, 괄호는 msg/s)

| 배치(메시지) | 지연/방향 | multirow-tx (현재) | multirow | unnest | copy |
| --- | --- | --- | --- | --- | --- |
| 300 | 0 ms | 12,500 (6,250) | 12,694 (6,347) | 12,751 (6,376) | 11,990 (5,995) |
| 1,000 | 0 ms | 12,665 (6,332) | 12,562 (6,281) | 12,507 (6,254) | 12,413 (6,207) |
| 3,000 | 0 ms | 11,214 (5,607) | 11,272 (5,636) | 11,450 (5,725) | 12,561 (6,280) |
| 300 | 20 ms | 3,016 (1,508) | 4,426 (2,213) | **5,263 (2,631)** | 2,035 (1,017) |
| 1,000 | 20 ms | 4,717 (2,358) | 5,917 (2,959) | **7,881 (3,941)** | 4,531 (2,266) |
| 3,000 | 20 ms | 5,528 (2,764) | 6,140 (3,070) | **7,593 (3,797)** | 6,602 (3,301) |

배치 하나의 p50 (현재 방식): 300건 47 ms → 20 ms 지연에서 196 ms, 1,000건 157 ms → 424 ms.

## 해석

1. **지연이 없으면 방식 차이가 없다.** 약 12,000~12,700 rows/s에서 모두 비슷하다. 이 한계는 DB 쪽 삽입 비용(하이퍼테이블, 인덱스 3개, 트리거)이고 COPY도 넘지 못한다. 배치를 키워도 3,000건에서는 오히려 약간 줄었다. **COPY는 이 스키마에서 이득이 없다.**
2. **지연이 있으면 왕복 수가 처리량을 정한다.** 현재 방식은 왕복 3회라 배치당 시간이 계산 시간 + 120 ms(왕복 40 ms × 3)에 가깝다(300건: 47 + 120 ≈ 196 ms 실측과 일치). `unnest`는 왕복 1회라 같은 지연에서 1.7배(1,000건)다.
3. 같은 모델을 TC-06 조건(방향당 100 ms, 왕복 200 ms)에 적용하면 현재 방식은 배치 300건에 약 47 + 600 = 650 ms, 즉 **약 460 msg/s**로 실측(약 540 msg/s 추정)과 같은 규모다. 이것이 1,000 msg/s 입력에서 큐가 넘친 직접 원인이다. `unnest`(왕복 1회)는 300건에 약 47 + 200 = 250 ms로 약 1,200 msg/s, 1,000건이면 약 160 + 200 = 360 ms로 약 2,800 msg/s로 **1,000 msg/s를 넘는다**(모델 계산이며 이 조건으로 직접 측정하지는 않았다).
4. 배치를 키우면 지연이 큰 환경에서는 이득이지만, 배치가 커질수록 한 번에 실패했을 때 이분법 비용과 ack 지연(한 배치가 커밋될 때까지 ack 대기)이 늘어난다. 지연이 없는 환경에서는 이득이 없다.

## 다음 단계 (결정 필요)

쓰기 경로 변경은 설계 결정이라 구현하지 않았다. 후보:

| | 내용 | 효과(위 모델) | 비용·주의 |
| --- | --- | --- | --- |
| 1 | 트랜잭션을 없애고 `unnest` 문장 하나로 저장 | 지연 환경에서 약 1.7배 | 문장이 원자적이라 불변식 1·3은 유지. GORM 대신 pgx 직접 사용 또는 Raw 쿼리 |
| 2 | 1 + 배치 크기 상향(300 → 1,000) | TC-06 조건에서 약 2,800 msg/s(계산) | 배치 실패 시 이분법 비용, ack 지연 증가, `max_inflight_messages`(600)와의 관계 재검토 |
| 3 | 현재 유지 | — | TC-06 5분 조건 미달 유지 |

이 결과를 TC-06 5분 조건으로 직접 검증하는 것은 선택한 뒤에 한다.
