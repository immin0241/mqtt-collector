# TC-19: 연속 집계(1분)와 압축의 조회 시간·저장 용량

- 날짜: 2026-11-14
- 목적: 1분 연속 집계(`sensor_data_1m`)와 3일 압축 정책이 조회 시간과 저장 용량에 주는 영향을 압축 전후로 비교한다.
- 한계: 조합마다 p50 5회(워밍업 1회 제외), 실행 1회. 경향을 보는 용도이며 통계적 의미는 없다. 보존(retention) 정책과 집계 압축은 **측정하지 않았다.**

## 조건

| 항목 | 값 |
| --- | --- |
| 장비 | AMD Ryzen 5 7500F (6코어 12스레드), RAM 15.8 GB, WSL2 위의 Docker. 클라이언트와 DB가 같은 머신 |
| DB | TimescaleDB 컨테이너, migration 000011~000012 (세로 구조, 인덱스·트리거·유니크 키 포함) |
| 데이터 | 센서 30개 × 지표 4개 × 10초 간격 × 14일(UTC 자정 정렬) = **14,515,200행** |
| 적재 | 서버에서 `generate_series`로 하루씩 INSERT: 14분 4초(17,205 행/s, 트리거·FK·인덱스 포함) |
| 집계 | `sensor_data_1m` 전체 갱신 18.7초. 정책 job(압축·갱신)은 멈추고 직접 실행 |
| 압축 | 기준 시각 3일보다 오래된 11개 chunk를 `compress_chunk`(segmentby `sensor_id, metric_id`, orderby `time DESC, seq DESC`): 9초 |
| 조회 | 센서 1개·지표 1개(분·시간 버킷), 전 센서 한 지표 통계. 원본 vs 1분 집계. p50 |
| 코드 | `test/experiments/aggregates_compression_test.go` |

## 저장 용량

| | sensor_data 테이블 | 인덱스 | 합계 | sensor_data_1m |
| --- | --- | --- | --- | --- |
| 압축 전 | 1,060 MiB | 1,742 MiB | **2,803 MiB** | 323 MiB |
| 압축 후 (11/14 chunk) | 259 MiB | 374 MiB | **725 MiB** | 323 MiB |

- 전체 합계는 3.9배 줄었다. 압축하지 않은 3개 chunk(최근 3일)가 포함된 값이므로, 압축한 chunk만의 비율은 이보다 크다(분리 측정은 하지 않았다).
- 원본 행당 약 193 B(인덱스 포함)이던 것이 약 50 B가 되었다. 합성 데이터(사인파 + 작은 노이즈)라 **실제 센서 값에서는 압축률이 다를 수 있다.**
- **집계(323 MiB)가 압축 후 원본 전체(725 MiB)의 44%다.** 집계는 압축하지 않았고 행당 약 134 B다. 집계 압축은 시험하지 않았다.

## 해석

1. **여러 센서를 훑는 질의에서 집계 이득이 크다.** 전 센서 통계는 압축 전 원본 기준으로 구간에 상관없이 약 6배(14일 1.1초 → 0.19초)다. 일일 리포트 같은 요약 조회는 집계를 읽는 것이 맞다.
2. **센서 1개 시계열은 이득이 작다**(압축 전 1.4~1.6배). `(sensor_id, time)` 인덱스가 이미 좁은 범위를 빠르게 찾아서 집계로 줄어드는 비용이 작은 것으로 보이나, 분리해서 확인하지는 않았다.
3. **압축하면 원본 조회가 빨라지는 경우와 느려지는 경우가 섞인다.** 전 센서 통계는 압축 후 원본이 2~3배 빨라졌다(558 → 268 ms, 1.1 s → 0.33 s). 압축 chunk를 읽는 I/O가 줄어든 것으로 보이지만 측정으로 분리하지는 않았다. 반대로 압축하지 않은 최근 1일의 센서 1개 원본 조회는 13 → 53 ms로 느려졌다(아래 관측 1).
4. **압축 후에는 집계와의 차이가 줄어든다**(14일 전 센서 통계 5.9× → 1.8×). 그래도 집계가 더 빠르다.
5. 집계 조회 시간은 압축 전후로 거의 같다. 집계 테이블은 압축하지 않았기 때문이다.

## 설명하지 못한 관측 (원인 미확인)

1. **압축하지 않은 최근 1일의 센서 1개 원본 조회가 압축 후 4배 느려졌다**(13.4 → 53.1 ms, 같은 데이터·같은 질의). 압축 후 `ANALYZE`로 통계가 바뀌어 계획이 달라졌을 가능성이 있으나 `EXPLAIN`으로 확인하지 않았다.
2. **집계의 "최근 1일" 조회(9.4 ms)가 "첫째 날"(1.4 ms)보다 6배 느리다.** 행 수는 같다(1,440). 원인 후보는 실시간 집계의 원본 확인 비용이나 캐시 상태이지만 확인하지 않았다. 7일·14일 구간의 집계 조회도 행 수에 비해 느리다(10,080행에 65 ms).

이 둘은 `EXPLAIN (ANALYZE, BUFFERS)`로 확인하기 전에는 결론을 내리지 않는다.

## 결론과 다음 단계

- **압축은 저장 용량을 크게 줄인다**(전체 3.9배, 합성 데이터 기준). 3일 정책은 유지해도 된다.
- **리포트·요약 조회는 집계를 읽는다.** MCP 리포트 도구(ADR-0014)는 이미 `v_sensor_data_1m`을 쓴다.
- 결정이 필요한 후보 (이 실험에서는 구현하지 않았다):

  | | 내용 | 비고 |
  | --- | --- | --- |
  | A | 집계(`sensor_data_1m`)에도 압축 정책 적용 | 집계가 압축 후 저장 용량의 44%. 압축된 집계 조회 시간은 미측정 |
  | B | 1시간·1일 집계 추가 | 14일 이상 구간 조회용. 저장·갱신 비용 증가 |
  | C | 보존 정책 도입 | 원본 N일 후 삭제 시 집계만 남는다. 복구 불가한 삭제라 정책 확정 필요 |
- 위 관측 두 개는 `EXPLAIN`으로 먼저 확인한다.
