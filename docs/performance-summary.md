# 성능 지표 요약

지금까지 측정한 성능 수치를 한곳에 모은 문서다. **새 측정이 아니라 각 실험 문서의 값을 옮긴 것**이며, 모든 값의 조건과 원문은 링크한 문서에 있다.

## 읽기 전에

- 장비: AMD Ryzen 5 7500F (6코어 12스레드), RAM 15.8 GB, **WSL2 위의 Docker 단일 호스트**. 클라이언트·브로커·DB·앱이 모두 같은 머신을 나눠 쓴다. 운영 환경 수치가 아니다.
- 대부분 **1회 실행**이고 통계적 의미는 없다. 경향과 자릿수를 보는 용도다.
- 스키마는 세로 구조(ADR-0012)다. 메시지 하나가 측정 행 둘(`tilt_x`, `tilt_y`)이므로 **msg/s와 rows/s는 2배 차이**가 난다. 아래 표에서 구분해 적었다.
- 설정: 배치 300건, `ChannelSize` 600, 브로커 `max_inflight_messages 600`·`max_queued_messages 200000`(TC-06 이후), persistence on.

| 배치(300건) 커밋 시간 | p50 **52.5 ms** / p95 59.5 ms | 위와 같은 조건 | [tc17-tenant-sessions](experiments/phase7-tc17-tenant-sessions.md) |
| 메시지당 측정 행 수의 영향 | 행 처리량은 약 11,300 rows/s로 일정, 행이 늘면 msg/s가 반비례(1행 11,079 → 2행 5,651 → 4행 2,862 msg/s) | 배치 300 | 위와 같음 |

**해석:** 지연이 없을 때의 한계는 DB 삽입 비용(하이퍼테이블, 인덱스 3개, 트리거)이다. 목표 1,000 msg/s의 5~6배라 여유가 크다.

## 6. 병목과 한계 (측정 근거 기준)

1. **DB 왕복 지연이 지배 요인이다.** 지연 20 ms에서 처리량이 지연 없음의 약 1/4로 떨어지고(배치 300: 6,250 → 1,508 msg/s), 왕복 1회 방식이 이를 1.7배 회복한다.
2. **지연이 없으면 삽입 비용(인덱스·트리거)이 한계**이고 배치 확대·COPY로는 넘지 못한다. 트리거 제거는 약 30% 여유를 준다(미적용).
3. **백프레셔가 발행 측까지 전달되지 않아** 수집 용량을 넘는 입력은 브로커 큐에 쌓이고, 큐가 넘치면 PUBACK 후에도 유실된다. 큐 상향은 유실 시점을 늦출 뿐이다.
4. 조회는 요약(여러 센서)에서 집계 이득이 크고(약 6배), 센서 1개 시계열은 작다(1.4~1.6배).

## 7. 아직 측정하지 않은 것

- 부하 상태의 **경보 지연 p99**(TC-08), 수집 지연 p99의 **부하별 곡선**
- **수평 확장**(TC-18: 공유 구독 1→2→4→8)과 **지속 처리량·장시간**(TC-10 30분, TC-11 2시간+)
- 보존 정책·집계 압축, CPU 사용률, 실제 센서 값의 압축률
- 일부 조회 이상값(TC-19의 두 건)은 원인 미확인
- 모든 수치는 단일 호스트 WSL2다. 서버급 장비·네트워크 지연이 있는 배치에서는 달라질 수 있다.
