# ADR-0008: 센서 상태 판정과 경보 평가

- 상태: 채택 (2026-10-23). 1~3은 사용자 결정, 4~7은 구현 중 내가 정한 기본값이며 검토가 필요하다.
- 관련: 불변식 4·5·6·7, RFP ECR-008 5), SFR-007, TC-08·12·13, migration 000007

## 결정

| # | 항목 | 결정 | 결정자 |
| --- | --- | --- | --- |
| 1 | 경보 평가 위치 | 수신 핸들러에서 메모리로 평가. DB 저장과 분리 | 사용자 |
| 2 | 스키마 | `alert_rule`(규칙) + `alert_event`(발생), `UNIQUE (rule_id, sensor_id, seq)` | 사용자 |
| 3 | 장애(faulty) 범위 | flatline + 범위 밖 반복. 진단 오류 코드는 제외 | 사용자 |
| 4 | 경보 발화 방식 | 정상 → 위반으로 바뀌는 순간에만 발화(edge trigger) | 구현자 기본값 |
| 5 | 경보 큐 포화 | 버리고 `alerts_dropped_total{reason="queue_full"}` 로 센다 | 구현자 기본값 |
| 6 | 전체 두절 | online 센서 3개 이상이 전부 동시에 한도를 넘기면 센서별 판정을 멈추고 `ingest_event(stalled)` 한 건 | 구현자 기본값 |
| 7 | 임계값 | flatline 연속 10회, 범위 밖 연속 3회, 타임아웃 = max(예상 주기 × 2, 최소값). 모두 환경 변수로 바꾼다 | 구현자 기본값 |

## 배경과 근거

**1. 수신 시점 평가.** 불변식 7(센서 상태는 수신 시점 기준)과 같은 이유로, DB가 느리거나 멈춘 동안에도 경보가 나가야 한다.
DB를 폴링하는 방식은 flush 주기와 재시도 시간만큼 경보가 늦어지고 DB 장애 중에는 평가가 멈춘다.
대가는 두 가지다. 규칙은 주기(기본 10초)로 다시 읽으므로 규칙 변경이 최대 그만큼 늦게 반영되고, 평가 상태가 메모리에 있어 재시작 시 사라진다.

**재전달 안전성.** 같은 메시지가 재전달돼 다시 평가되어도 후보는 같은 `(rule_id, sensor_id, seq)` 이고
`INSERT ... ON CONFLICT DO NOTHING` 이 흡수한다. 재시작 때 위반이 이어지던 센서는 상태가 사라져 첫 메시지에서 경보가 한 건 더 생길 수 있다(4와 관련).

**4. edge trigger.** 위반 중인 센서가 초당 한 건 보내면 메시지마다 경보를 만드는 방식은 경보 폭주다.
한 번 어긴 뒤 정상으로 돌아올 때까지는 한 건이다. 정상으로 돌아왔다가 다시 어기면 새 경보다.
대안(매 메시지 발화 + 쿨다운)은 쿨다운 시간이라는 새 파라미터가 필요하고 같은 위반의 경보가 여러 건이 된다.
이 결정은 "위반이 길게 이어져도 운영자에게는 한 건"을 택한 것이다. 반대가 필요하면 `Evaluate`의 발화 조건만 바꾸면 된다.

**5. 큐 포화 시 드롭.** 경보 평가가 수신 핸들러에서 실행되므로 큐가 차면 선택은 "핸들러를 막는다"와 "버린다"뿐이다.
막으면 수집이 멈추므로(불변식 2의 백프레셔는 DB 장애 대응이지 경보 기록 때문이 아니다) 버린다.
기본 큐는 1,000건이고, 평가 결과는 위반 순간에만 나오므로 정상 운영에서는 거의 차지 않는다.
드롭된 경보는 `alerts_dropped_total` 로만 남고 DB에는 없다. 이 지표가 0이 아니면 경보가 누락됐을 수 있다.
종료 시 못 쓴 경보(`reason="shutdown"`)는 재시작 후 재전달된 메시지가 다시 평가하며 되살아난다.

**6. 전체 두절 판정.** 브로커 연결이 끊긴 동안은 이미 판정을 멈춘다. 그러나 연결은 살아 있는데 데이터만 안 오는 경우
(발행 측 장애, 네트워크 분리)도 센서 수백 개가 한꺼번에 offline 이 되면 안 된다. 센서가 2개 이하이면 "전부"가 우연히 같을 수 있어 개별 판정을 유지한다.
복구 시 online 이던 센서의 `last_seen` 을 현재로 당겨 첫 판정에서 오탐이 나지 않게 한다.
한계: 센서가 3~4개뿐인 작은 시설에서는 "전부 조용"이 실제 개별 고장 동시 발생일 수도 있다.

**faulty 정의.** offline(통신 오류)과 구분한다. 데이터는 오지만 값이 믿을 수 없는 상태다.
- flatline: 측정 채널 전체가 직전과 같은 값이 연속 N회.
- 범위 밖: 정상 범위(tilt ±30°, crack 0~50mm, temperature −40~85℃) 밖의 값이 연속 M회. 한 번만 튀는 값은 장애로 보지 않는다.
- 해소: 두 조건이 모두 풀리는 첫 메시지. 접속(LWT online)만으로는 풀리지 않는다.
- faulty 센서도 침묵하면 타임아웃으로 offline 이 된다.
- 범위는 센서 사양에 따라 달라야 하지만 지금은 전역 기본값이다. 센서별 범위는 `sensor` 컬럼으로 옮기는 후속 작업이다.
- 실제 센서는 정지한 구조물에서 정상이어도 분해능 한계로 같은 값을 반복할 수 있다. flatline 연속 횟수는 그 센서의 분해능과 구조물 거동에 맞춰 조정해야 한다.

**재시작.** 시작 때 `sensor_status` 를 읽어 online/faulty 였던 센서는 `last_seen` 을 현재로 두고 복원한다(유예).
복원하지 않으면 모두 unknown 으로 시작해, 재시작을 가로질러 조용해진 센서는 영영 판정되지 않는다(통합 테스트가 이 경우를 검증한다).
복원 실패는 수집을 막지 않고 로그만 남긴다.

## 결과

- 경보 상태: `open → in_progress → resolved` 만 허용. `UPDATE ... WHERE id = ? AND status = ?` 의 영향 행 수로 판정하므로 동시 요청 중 하나만 성공한다.
- 지표: `sensors_by_state{state}`, `alert_latency_seconds`, `alerts_created_total`, `alerts_deduped_total`, `alerts_dropped_total{reason}`.
- 운영 이벤트: `ingest_event(stalled/resumed/broker_down/broker_up)`.
- 알려진 한계: 경보 규칙의 변경률은 센서·규칙별 표본 2,048개까지만 기억한다(불변식 4). 창 안에 표본이 더 많으면 오래된 쪽부터 버려 창이 짧아진다.
