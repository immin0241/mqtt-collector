# ADR-0001: MQTT ack 시점과 방식

- 상태: 채택 (2026-10-23, 사용자 결정 A)
- 관련: 불변식 1, TC-02/03/04, `docs/notes/paho-manual-ack.md`

## 맥락

자동 ack는 핸들러가 반환하는 즉시 PUBACK을 보낸다. 이후 DB 커밋에 실패하거나 프로세스가 죽으면 브로커는 이미 전달 완료로 보고 메시지를 지운다. 유실이다.

## 선택지

| | 설명 | 장단점 |
| --- | --- | --- |
| a | 커밋 후 메시지별 개별 `Ack()` | 구현 단순. ack 호출 시점이 메시지마다 갈릴 수 있다. |
| **b (채택)** | 배치 커밋 후 그 배치의 메시지를 수신 순서대로 한꺼번에 `Ack()` | 커밋과 ack의 경계가 배치 하나로 일치해 추론이 쉽다. |

MQTT 3.1.1에는 다중 ack 패킷이 없으므로 "일괄"은 배치 커밋 직후 PUBACK을 연속 전송한다는 뜻이다.
사용자 응답이 "(a) 커밋 후 일괄 ack"였고 표의 (a)와 문구가 어긋나, 문구("일괄 ack")를 따라 b로 해석했다. 이 해석은 계획 승인 시점에 명시되어 있었다.

## 결정

- `SetAutoAckDisabled(true)`. 데이터 메시지는 `DbPushWorker`가 배치 커밋(또는 격리 기록) 성공 후에만 ack한다.
- 파싱 실패 메시지도 격리 테이블에 기록한 뒤 ack한다.
- 상태 토픽(`.../status`)은 DB와 무관하므로 핸들러에서 즉시 ack한다. 자동 ack를 껐을 때 ack하지 않으면 브로커 inflight 창이 막힌다.
- 커밋에 실패한 배치는 ack하지 않는다.

## 결과

- 커밋과 ack 사이에 죽으면 재전달되어 중복 수신된다. `UNIQUE (sensor_id, seq, time)` + `ON CONFLICT DO NOTHING`이 흡수한다. (at-least-once + 멱등 저장)
- 연결이 끊긴 뒤의 `Ack()`는 paho가 에러 없이 버린다. 이 경우도 재전달 + 중복 제거로 수렴한다.
